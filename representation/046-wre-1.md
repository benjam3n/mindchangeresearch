## Stage 0 — artifact definition

Type: checkpoint card. Venue: a route-review packet accompanying the declared decoder. Reader: a reviewer who knows ordered pairs and compass headings but has only the saved checkpoint and remaining command string. Reader baseline: integer addition; no hidden legend or earlier route history. Writer goal: make one continuation executable and auditable. Core unresolved question: Which saved state makes this relative continuation determine one endpoint? Scope: endpoint recovery under this decoder, not human navigation, path safety, or a universal notation. Stakes: omitting heading or order permits distinct endpoints.

## Stage 1 — thesis object

Core thesis: Under the declared decoder, the checkpoint `(position=(2,3), heading=east)` plus the ordered suffix `FRFF` determines the final state `(position=(3,1), heading=south)`.

Claim type: explanatory/technical. Weaker claim: route instructions need some context. Stronger claim refused: every route should use relative commands and store body heading; refused because a compass-only route can determine displacement without body heading. Actual defended claim: position, heading, decoder and suffix order are sufficient for this relative-route instance.

Supporting claims: C1 `F` uses current heading; required to translate tokens into displacement. C2 `R` updates heading before later `F`; required by the held-out result. C3 ordered execution matters; required because `FRF` and `RFF` differ. Out of scope: O1 added body-turn words improve a reviewer’s accuracy; no reader data. O2 the endpoint proves all intermediate restrictions were obeyed; two paths can share an endpoint. O3 the notation is optimal across maps or readers.
