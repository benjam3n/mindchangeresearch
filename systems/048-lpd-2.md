# Bridge evidence granularity to action granularity

Starting judgment: Given a finding that an approach worked in one setting, my next useful move would be to describe that success and let the selector consider it. That leaves a consequential mismatch between the evidence unit and the proposed action unit.

Actor and scope: The assistant's current working representation and operations in this systems line. This record does not establish human effects, model-weight changes, or transfer to another session.

Source: `../sources/systems-lpd.md`; current requirements are retained separately in `../sources/systems-lpd.requirements.txt`.

Depth: The original defines no numerical 8x floor. The expanded execution below covers the actual operations and multiple dependencies/countercases; no numerical 8x certification is asserted.

Landscape: an observed demonstration supplies one result; a selector chooses an intervention; a setting supplies timing, task and available evidence; an action controller commits the selected output. Information is trapped when the result says only "worked" while the controller must decide where and when.

Concrete input: a comparison table correctly resolves a lookup task when all options and criteria are given. A later task asks for open-ended discovery of missing options. The original result has no discovery trial. The two systems differ in format (success label versus eligibility conditions), access (selector lacks original input) and timing (choice occurs later).

Arbitrage search across pairs: result→selector offers an evidence-scope bridge; setting→controller offers availability data; source→result offers procedure identity. There is no price, geographical or market opportunity. Insertion search: unreliable generalization occurs at eligibility, not in the already correct table computation. A second full explanation of the table adds little; a fit predicate directly joins result scope to action conditions.

Additional types: standardization can make input conditions explicit; aggregation can combine several scoped results; automation can evaluate declared conditions; optionality retains discovery as a separate candidate; learning requires new results, not just retained metadata. Network, scarcity and commercial defensibility have no established role.

Actual transformed decision: eligibility predicate is `task == lookup and options_given and criteria_given`. It accepts the observed lookup configuration. It refuses the open-ended discovery configuration even if both share the label "comparison." The action controller therefore routes the discovery input to option generation; it retains table use after options and criteria exist. Six cases, including missing criteria and irrelevant task label, are evaluated in `scope-bridge.json`.

Countercase: this predicate is sufficient only for eligibility under the present evidence, not proof the table succeeds on every accepted case. Correct rejection of an unsupported transfer is the demonstrated change.

Actual mind change: The later discovery task no longer inherits a lookup result merely because both are called comparison.

Benefit: The executed six-case predicate distinguishes the demonstrated setup from unsupported transfer cases while preserving exact setup reuse. Human transfer is still unknown.

Verdict: KEEP

Organization: A condition-indexed result joins evidence to a choice; a success-only sentence loses that relationship.
